01 / COMPUTE

The GPU is a first-class citizen now

The field of particles behind the headline isn't a video, and it isn't drawn by the CPU. It's a WebGPU compute shader — the same class of hardware access that powers game engines and ML runtimes, running in a plain browser tab.

WebGPU · WGSL

A flow field, simulated on-device

Every frame, a compute pass moves each particle through a curl-noise vector field — a divergence-free flow that behaves like idealized smoke. Your pointer adds an attractor; pressing down flips it into a repulsor. All of it happens in WGSL, WebGPU's shading language, without a single particle ever touching JavaScript.

By mid-2026 WebGPU ships in Chrome, Edge, Firefox and Safari. Where it's unavailable, this page quietly falls back to a WebGL2 fragment shader — resilience is part of the craft.

// WGSL — the actual kernel running behind the hero
fn flow(p: vec2f, t: f32) -> vec2f {
  let e = 0.06;
  let s = p * 1.4 + vec2f(t * 0.06, -t * 0.04);
  let dx = fbm(s + vec2f(e, 0)) - fbm(s - vec2f(e, 0));
  let dy = fbm(s + vec2f(0, e)) - fbm(s - vec2f(0, e));
  return vec2f(dy, -dx) / (2.0 * e); // curl ⇒ swirls, never sinks
}
Architecture

Why compute changes the ceiling

WebGL could only pretend to do general computation, smuggling data through textures. WebGPU has real storage buffers, real workgroups, and a modern binding model. The simulation here dispatches one thread per particle — hundreds of thousands of them — in well under a millisecond per frame.

The particles are then drawn as instanced quads with additive blending, colored by their own velocity: fast particles run hot into magenta, slow ones cool into deep blue. The palette is computed in the shader, in linear light, and matches the OKLCH accents used by the CSS around it.

The practical takeaway: physics, fluid sims, on-device inference and non-trivial creative coding no longer need a native app. The tab is enough.

02 / LIGHT

Signed distance fields, marched in real time

This object doesn't exist as geometry. There are no triangles, no mesh, no 3D model file — just a mathematical distance function evaluated per-pixel, per-frame, in a GLSL fragment shader. Drag it.

raymarched sdf · webgl2 · drag to orbit
GLSL · Raymarching

Sculpting with math

A ray leaves the camera for every pixel and repeatedly asks one question: how far is the nearest surface? The scene answers via a signed distance function — here, a sphere and a cube blended with a smooth-minimum, orbited by a torus, rippled by a sine field. Change the function, change the sculpture.

// the entire "model" — no vertices anywhere
float map(vec3 p) {
  float body  = mix(sdSphere(q, .62), sdBox(q, vec3(.48)), m);
  float ring  = sdTorus(r, vec2(.95, .14));
  return smin(body, ring, .28) + ripple;
}
Rendering

Lighting from first principles

The surface normal is recovered by sampling the distance field four times in a tetrahedron pattern — calculus by finite differences. From there it's classic optics written by hand: a key light, a Fresnel rim that brightens grazing angles, a specular highlight, and distance fog blending into the backdrop.

Nothing here is a "material" from a library. Every photon-shaped decision is ~40 lines of GLSL you could read over coffee, and the same technique scales up to the fractal worlds you see on Shadertoy — the demoscene's gift to the web platform.

03 / SCROLL

Scroll is a timeline now

Every reveal, every parallax drift on this page — and the gradient progress bar pinned to the top — runs on CSS scroll-driven animations. No scroll listeners. No jank. The compositor owns the whole effect.

animation-timeline

Declarative, off-main-thread

For fifteen years, scroll effects meant JavaScript: listen, measure, mutate, pray you finish in 16 ms. Scroll-driven animations invert that. You declare that an animation's clock is the scroll position — scroll() for the page, view() for an element's journey across the viewport — and the browser runs it on the compositor thread, immune to main-thread stalls.

/* the progress bar at the top of this page */
.progress {
  animation: grow-x linear both;
  animation-timeline: scroll(root);
}
/* every card you've watched fade in */
[data-reveal] {
  animation-timeline: view();
  animation-range: entry 5% entry 65%;
}
scroll-state()

The header knows it's stuck

Scroll up a little and watch the navigation bar: the moment it pins, it grows a frosted-glass background and a hairline border. That's not an IntersectionObserver — it's a scroll-state container query: @container scroll-state(stuck: top) lets CSS style an element based on whether its sticky positioning has actually engaged.

The same query family can detect elements snapped by scroll-snap and containers that are scrollable at all — a whole class of "state the browser already knew but never told CSS about," finally exposed.

Graceful degradation is built in: on a browser without support, the nav simply stays transparent. Nothing breaks; the experience just sheds one nicety.

04 / COLOR

Out of the sRGB cage

Every color on this page is authored in OKLCH — a perceptual space where "same lightness" actually looks like the same lightness — and the accents reach into Display P3, the wide gamut your screen has probably had for years while the web ignored it.

oklch()

Twelve hues, one lightness

Below: hue rotates 0→330° while lightness and chroma stay fixed at oklch(72% 0.17 h). In HSL this ramp would pulse bright at yellow and collapse dark at blue. In OKLCH it stays visually even — which is why design systems migrated en masse.

display-p3 · light-dark()

Wider gamut, fewer theme forks

These two greens are both "maximum green" — the left one in sRGB, the right in Display P3. On a wide-gamut screen the P3 swatch is visibly more saturated; on an sRGB screen they match. Same CSS, honest hardware.

Theming, meanwhile, collapsed into one function. This page's entire palette is declared once with light-dark() — flip the theme with the button in the header and no selector rewrites fire, just the other value of each token:

--bg:  light-dark(oklch(97% .005 250),
                  oklch(14% .02 265));
--ink: light-dark(oklch(22% .02 260),
                  oklch(94% .01 250));
05 / LAYOUT

Components that think for themselves

The unit of responsive design is no longer the viewport — it's the component. Containers query their own size, tooltips tether and flip themselves, and height animates to auto like it always should have.

@container

One card, two layouts, zero media queries

This demo card restyles itself based on its own width, not the screen's. Grab the handle on its right edge and squeeze it — watch it reflow from side-by-side to stacked as it crosses 34rem.

layout:

A component written this way is truly portable: drop it in a sidebar, a modal, a three-column grid — it adapts to the space it's given, because it's querying the container it lives in, not the device it happens to render on.

anchor positioning

Tooltips without a geometry library

Positioning a floating element used to mean shipping a JavaScript engine to measure rects every frame. CSS anchor positioning replaces all of it: the tooltip below declares position-anchor, sits in the block-start area, and position-try-fallbacks: flip-block makes it flip below the button on its own if it would ever clip the viewport.

Tethered, aligned, and auto-flipping — zero lines of positioning JavaScript. I'm a popover="hint", so I can't steal focus, and light-dismiss is free.
interpolate-size

The end of the height:auto hack

These accordions animate open to their natural height with pure CSS — interpolate-size: allow-keywords finally lets transitions target intrinsic sizes. Also note the native ::details-content pseudo-element doing the clipping.

Why did this take fifteen years?
Animating to auto requires the engine to resolve layout before the transition starts — a chicken-and-egg problem that calc-size() and interpolate-size formalized. Opting in is one line on :root.
What's doing the animation here?
A transition on block-size from 0 to auto, plus content-visibility transitioning with allow-discrete so the content stays paintable for the whole ride. No max-height guesses, no JS measurement.
Does it degrade?
Perfectly. On engines without support, these are ordinary <details> elements — they still open and close instantly. Enhancement, not dependency.
popover · @starting-style · view transitions

Motion the browser handles for you

The button below opens a top-layer popover — focus-managed, light-dismissed, promoted above everything — animated in with @starting-style and animated out with transition-behavior: allow-discrete, the pair that finally made entry/exit animations declarative. And the theme toggle in the header? That's the View Transitions API snapshotting the whole page and sweeping the new theme in as an expanding circle from your cursor.

popover

Hello from the top layer

No z-index wars, no focus-trap library, no click-outside handler. Esc or click away to dismiss — the platform does the choreography, and @starting-style gave me an entrance.
